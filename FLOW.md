# Execution Flow

## Phase 1 data flow

`src/audit_phase1.py` calls `load_ibtracs()` in `src/ibtracs.py`, then `filter_north_atlantic()`, then `build_forecast_samples()` for each horizon.

The loader skips the IBTrACS units row and parses timestamps/numeric USA fields. Filtering keeps the audited North Atlantic HURDAT states. Sample construction groups rows by `SID`, requires five contiguous six-hour historical states plus a valid future state, derives history-only motion features, and returns direct displacement/wind-change targets with metadata.

`storm_split_map()` assigns each `SID` atomically to train, validation, or test after split boundaries are selected.

## Phase 2 baseline flow

`python3 -m src.run_baselines <csv>` loads the Phase 1 sample sets, assigns whole-storm chronological splits, fits/selects ridge only on training and validation rows, and scores every baseline on the identical test rows. `src/evaluation.py` reconstructs predicted coordinates before applying Haversine track error and wind MAE/RMSE. The final run fixes history to five states (24 hours), evaluates +6/+12/+24/+48-hour targets, and writes `results/track_only_baselines.csv`.

## Phase 3 GRU flow

`python3 -m src.run_gru <csv>` uses the same filtered samples and split map as Phase 2. For each horizon, `src/gru.py` fits normalization statistics on training rows, trains width-16 and width-32 GRU candidates, selects the best validation checkpoint, and predicts the unchanged test rows. The final runner evaluates GRU and all three baselines through `src/evaluation.py`, writes `results/track_only_gru_comparison.csv`, and `src.plot_track_results` renders its track-error SVG without another dependency.

## Held-out error-analysis flow

`python3 -m src.run_error_analysis <csv>` recreates exactly the final split and selected-model procedure, but changes no settings and writes no model state. `src.error_analysis.error_rows()` combines each test origin’s source metadata, reconstructed prediction, track error, wind error, and descriptive intensity/motion/wind-change categories. `summarize()` writes aggregate and conditional tables, with storm-clustered bootstrap intervals; it never treats serial windows as independent storms.

## Archived evaluation-report flow

`make evaluation-report` calls `src.report_evaluation` on the existing held-out error-analysis CSVs only. It reuses `summarize()` for the model×horizon table and its storm-level bootstrap CIs, carries forward the archived motion/intensity/intensity-change and annual summaries, and joins GRU/Ridge rows on identical `(SID, issue_time, target_time, horizon)` keys. The paired contrast then bootstraps whole-storm mean deltas with seed 42. Its SVG plots read those report tables; no model or data pipeline runs.

## Static research-replay frontend flow

`make frontend-data` calls `src.export_replay.build_payload()` on existing `results/track_only_error_analysis/held_out_errors.csv` and `overall.csv`, with the locally available official IBTrACS CSV only to map each SID to its real name, basin, and ATCF ID. The exporter groups repeated per-model rows into one observed IBTrACS track per SID and one forecast set per issue time/horizon, retaining target states, predictions, and archived errors. `frontend/app.js` loads that payload and the bundled local country-boundary topology, renders an SVG geographic map with pan/zoom/fit, and binds every observed timestamp to slider, scrub, click, and playback state. `togglePanel()` independently changes the collapsed panel class and the corresponding map workspace margin, then redraws after the layout transition. `make serve` exposes the static directory only; no model execution occurs in the browser.

## Phase 4 history-ablation flow

`python3 -m src.run_history_ablation <csv>` builds 2/3/5/7/9-state samples through the existing Phase 1 builder. Each length keeps its own eligible training windows, while `align_common_origins()` limits validation and test evaluation to shared `(SID, issue_time, target_time)` keys. The GRU selection procedure remains unchanged; the runner chooses the lowest common-validation track error per horizon and writes `results/phase4_history_ablation.csv`.

## ERA5 acquisition and extraction flow

This is retained historical implementation only. ERA5/CDS is frozen and is not part of the current experiment or execution plan.

`python3 -m src.acquire_era5 <csv> --concurrency 4` rebuilds the selected-history origin union using `(horizon, history_steps) = (6,9), (24,7), (48,9)`, deduplicates it by `(SID, issue_time)`, then retains September--October dates in `request_manifest_sep_oct.csv`. It groups those dates into 264 monthly pressure-wind, humidity, and SST CDS requests. The repository-canonical `data/raw/era5/v1` directory owns the process lock and atomically persisted journal even when `--raw-dir` changes output storage. The lock-owning coordinator validates cached targets, journals canonical payload/fingerprint/dataset before `retrieve()`, and durably records each returned datastore job ID. It queues at most four independent recorded jobs at once; each worker has a private CDS client and job-specific `.part` file, while only the coordinator atomically saves returned job state. If submission returns an ambiguous error without an ID, resume paginates account jobs and compares each server request to the journaled payload; exactly one match is journaled and joins the queue, while zero or multiple matches abort without `retrieve()`. A successful job obtains `Remote.get_results().location` and `content_length`; `curl --continue-at -` writes the same job-specific `.part` file, with three retries and 900-second transfer/retry limits. The parent checks byte count, validates, and atomically promotes only a successful attempt. Exhaustion records `download_error` without replacing the job; independent queued jobs finish, then the CLI exits non-zero before validation or feature extraction. `extract_features()` receives the same September--October origin subset, so cached off-season files cannot enter `results/phase5_era5_features.csv`. A failed validation or CDS job aborts before feature extraction; no missing value is imputed.

## Metadata-only TCC genesis feasibility audit

`python3 -m src.audit_genesis <tcc_ibtracs.csv> <ibtracs.ALL.list.v04r01.csv> --output <manifest.csv>` reads metadata only. `load_tcc()` retains `source=1` and `source=2`; `build_manifest()` first validates same-number TCC/source=2 track joins by their 3-hour seam and endpoint distance, then `_links()` maps source=2 continuations to official IBTrACS at exact timestamps within 1,000 km. It selects the SID with most coincident fixes then the shortest closest-point distance, failing closed on exact ties and excluding single-fix matches. Linked rows use official `USA_WIND` for first 34-kt time and require IBTrACS wind follow-up for negatives. Unlinked `devflag=0` tracks can receive a negative only with complete TCC follow-up; this lifetime status is audit-label evidence, never an input. Nine TCC timestamps and current TCC position end at issue time; no future IB position or genesis location enters the inputs. Whole TCC tracks use the 1982–2007 / 2008–2011 / 2012–2018 splits, with +24h boundary purging. `basin=UNKNOWN` stays explicit, and the recommended basin-resolved cohort excludes it. `report()` prints full and basin-resolved split totals plus basin/year counts; the CLI writes the manifest and sibling `genesis_counts_by_basin_year.csv`. Outputs remain separate from the frozen track-only experiment.

## Basin-resolved genesis GridSat/ERA5 preflight

`python3 -m src.preflight_genesis results/genesis_candidate_manifest.csv --output results/genesis_preflight.json` rejects any cohort other than the accepted 1,276 non-`UNKNOWN` rows, expands each stored nine-frame history, and paginates the official NOAA GridSat S3 `ListObjectsV2` index for the represented years. Each annual listing is cached in `results/gridsat_s3_index/<year>.json`, so `--cache-year YEAR` safely resumes a constrained audit. `build_report()` compares exact GridSat-B1 object keys against every unique input timestamp, lists every missing timestamp and candidate row it blocks, and sums object sizes without opening a frame. THREDDS HTTPServer, OPeNDAP, WCS, and NetCDFSubset remain later retrieval choices, not availability authorities. It separately validates the five compact ERA5 predictors against the documented hourly global 0.25-degree grid and the fixed 5x5-degree local patch. An index fetch error terminates the command before output: it must never convert an unreachable index into a missing-frame result. Nothing calls `acquire_era5`, CDS, training, or any imagery download.

The remote-patch path must first use NCEI NCSS or OPeNDAP to request `irwin_cdr` over a 96x96 patch around each historical TCC fix. The 2026-09-12 POC stopped at the metadata request because the official THREDDS endpoint timed out. S3 byte ranges are not a substitute: a GridSat object is HDF5/NetCDF and patch-specific bytes are not discoverable without its HDF5 chunk index. No remote patch, source frame, or derived tensor has been downloaded.

## Genesis ERA5 geo-chunked point-read POC

The metadata-only preflight was followed by one bounded read using the official ECMWF geo-chunked pressure store and single-level SST store. The input is `results/genesis_candidate_manifest.csv`; only rows with `basin != UNKNOWN` and exact 00/06/12/18 UTC issue times are eligible for pressure-level matching (384 rows). The probe opened the documented Zarr stores with xarray and the existing CDS bearer credential, resolved candidate 100017 to the exact 1982-03-15 18Z source time and nearest -12.25/54.5 grid cell, and attempted `u@850`. The value chunk GET timed out after 20.78 seconds; the Zarr adapter returned NaN fill, so the code stopped before requesting remaining fields or writing features. SST metadata was inspected but no SST data chunk was requested. No extraction implementation was added. Detailed request status, units, chunk shapes, measured metadata bytes, and the accounting limitation are in `results/genesis_era5_poc_audit.json`.

## South Asian LPS–TCC crosswalk audit

`python3 -m src.audit_lps_tcc_crosswalk --manifest results/genesis_candidate_manifest.csv --tcc-source /private/tmp/tcc_ibtracs.csv --lps-catalogue <local-parquet-or-csv>` uses the accepted manifest, `load_tcc()` for the merged TCC source, and only the catalogue columns `row_id`, `track_id`, `time`, detected-center lat/lon, position source, 850-hPa vorticity, and 700-hPa RH. It expands each manifest window to nine source=1 TCC positions, deduplicates repeated `(track,time)` points, then groups matches by exact UTC timestamp. The 1-degree great-circle threshold is 111.195 km. It accepts only a unique nearby detection that is not shared by another TCC position; all other cases remain unmatched/ambiguous. LPS identity validation is scoped to `(time,row_id)`, since the catalogue reuses row IDs at different hours. LPS intensity/category fields are excluded. On success it writes row and position CSVs plus JSON/Markdown reports under `results/lps_tcc_crosswalk/`. For the local Parquet, a lazy Polars projection/time filter generated a 4,741-row exact-time CSV because this Python environment has no pandas Parquet engine. The completed audit found no full histories; see `FEATURES/FEATURE-009-lps-tcc-crosswalk-audit.md`.

## TCC genesis ERA5 request-manifest flow

`python3 -m src.manifest_genesis_era5 results/genesis_candidate_manifest.csv results/lps_tcc_crosswalk/tcc_positions.csv --output results/genesis_era5_request_manifest.json` selects exactly the accepted 1,276 non-`UNKNOWN` rows through `cohort()`, verifies every nine-step 3-hour history and exact `(track,time)` position key, and checks issue-time coordinates against the frozen manifest. Shared history references are deduplicated by `(TCC track,time)`. Each unique track×UTC-day group creates one hourly pressure-level payload and one separate hourly SST payload. Its local dynamic bounding area is the outward-rounded union of the 5° crop footprints, including circular longitude handling across the dateline. Payloads use the existing canonical JSON/SHA-256 helpers; deterministic request keys and exact crop centers are saved with a source-row fingerprint for labels/splits. The JSON is written atomically and can be checked with `--validate-only`. This stage is metadata-only: it does not construct a CDS client, call `retrieve()`, download files, or crop values. A future acquisition path must send these specs through the existing `src.acquire_era5` lock/journal/recovery safeguards.

## TCC genesis ERA5 durable raw-acquisition flow

`python3 -m src.acquire_era5 --genesis-manifest results/genesis_era5_request_manifest.json --raw-dir <directory>` calls `genesis_file_specs()`, which checks the schema, deterministic request key, date fields, canonical payload fingerprint, expected dataset/variables/levels, and output format before it returns a spec. `acquire()` locks the canonical state directory and validates cached targets. Optional `--limit-new N` chooses at most N specs absent from both the journal and raw directory while holding that lock, and the CLI validates only those selected specs. For each new Genesis POST, `_submission_client()` creates a CDS client with a fresh Requests session, `(10, 90)` connect/read timeout, and `retry_max=1`; this is scoped away from Phase 4 submissions and recorded-job recovery. Before any Genesis POST, resume gathers existing no-ID non-DNS entries, builds one bounded read-only CDS history snapshot, then applies their exact persisted payload match locally; exactly one unclaimed job ID is atomically journaled and recovered, while zero/multiple matches remain unresolved. A history read error leaves every candidate unresolved and continues normal resume without a POST. Recorded DNS-resolution failures are eligible for retry only when the error positively identifies pre-CDS hostname resolution failure; the prior attempt is kept in `submission_history`. New no-ID failures and other old ambiguities remain unresolved without resubmission. Duplicate job IDs are rejected. Phase 4 submission and recovery behavior is unchanged. Recorded IDs recover through job-specific `.part` files. Successful results are byte-checked, validated against exact manifest times/variables/units/levels and circular longitude coverage, and atomically promoted. The CLI skips validation only for the returned unresolved keys and reports them with acquisition counts. No extract/crop stage follows this command yet.
